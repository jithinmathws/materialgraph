Append-only remediation and verification evidence. Current status is authoritative only in `../AUDIT_REGISTER.md`.

# MG-AUD-093

Title

Public validation accepts nonexistent chemical symbols

Status

✅ Resolved

Resolution Version

Post-v1.9.18

Affected Components

- Canonical periodic-table domain data
- Shared discovery element-filter dependency
- Seven discovery GET routes
- `avoid_element` and `prefer_element` query parameters
- Domain and API regression tests

Root Cause

Public discovery routes applied only string-length constraints to element
filters. Structurally valid but nonexistent symbols could therefore enter
discovery processing. The database could not serve as the validator because
its element table contains only the subset currently represented by imported
MaterialGraph data, not the full periodic table.

Resolution

✓ Added a centralized catalogue of all 118 recognized chemical element
symbols.

✓ Added canonical symbol normalization, including conventional casing and
surrounding-whitespace normalization.

✓ Added one shared FastAPI dependency that validates and normalizes both
element-filter parameters.

✓ Applied the dependency consistently to candidates, chains, graph, subgraph,
path, connected-community, and modularity-community routes.

✓ Preserved the distinction between chemical legitimacy and dataset coverage:
a valid symbol such as `Cu` is accepted even when no current material record
uses it, while an unknown symbol such as `Xx` returns `422`.

Regression Verification

✓ Domain tests verify that the catalogue contains exactly 118 symbols,
including `H` and `Og`, and that every canonical symbol normalizes to itself.

✓ Domain tests verify mixed-case normalization, surrounding-whitespace
normalization, and rejection of nonexistent symbols.

✓ API regressions cover all seven affected routes and both element-filter
parameters.

✓ The focused tests, full regression suite, and Ruff checks passed.

API Contract

Yes. Nonexistent chemical symbols now receive `422`, and accepted symbols are
normalized before reaching discovery services. Valid symbols are not rejected
merely because MaterialGraph has no current dataset coverage for them.

Database Migration

No.

Scientific Impact

Invalid element-filter requests can no longer influence discovery results.
No scoring, ranking, graph, or pathway algorithm changed. This remediation
validates symbol identity only; it does not claim that MaterialGraph contains
research data for every recognized element.

Lessons Learned

Chemical-domain validity and current database coverage are separate concerns
and require separate representations. A partial research dataset must not be
used as the authority for the existence of chemical elements.

# MG-AUD-060

Title

Pending graph-job claiming is not concurrency-safe

Status

✅ Resolved

Resolution Version

Post-v1.9.18

Affected Components

- `GraphJobService.claim_next_pending_job()`
- PostgreSQL graph-job claim transactions
- Multi-worker graph-job execution
- Graph-job service integration tests
- Isolated PostgreSQL test-database procedure

Root Cause

The service selected the oldest `PENDING` job and changed it to `RUNNING`
without locking the selected row. Two workers could therefore read the same
pending row before either transaction committed, allowing duplicate execution.

Resolution

✓ Added `FOR UPDATE SKIP LOCKED` to pending-job selection.

✓ Restricted selection to `PENDING` jobs and retained a one-row claim limit.

✓ Added a stable final job-ID tie-breaker after creation time so equal-time
claims remain deterministic.

✓ Changed the selected job to `RUNNING`, recorded its start time, and committed
the claim transaction before returning the job to a worker.

Regression Verification

✓ PostgreSQL integration coverage verifies that a locked oldest job is skipped
and the next eligible pending job is claimed.

✓ PostgreSQL integration coverage verifies that no job is returned when the
only pending job is locked by another transaction.

✓ Service regressions verify that a claimed `RUNNING` job is not claimed again,
that two pending jobs are claimed in deterministic oldest-first order, and
that no-pending-job behavior returns `None`.

✓ The focused graph-job tests and the full regression suite passed against the
isolated PostgreSQL database `materialgraph_test`.

Test-Database Safety Evidence

The temporary Windows Command Prompt `DATABASE_URL` override was verified
before migrations, seeding, and tests:

```cmd
py -c "from app.core.database import engine; print(engine.url.database)"
```

The deterministic reference baseline was restored and verified before the
full suite:

```text
materials: 28
material 5: (5, 'mp-19017', 'LiFePO4')
```

After testing, the temporary override must be removed in the same Command
Prompt so normal `.env` configuration becomes authoritative again:

```cmd
set DATABASE_URL=
```

The effective database must be verified before any subsequent migration,
seeding, development, or deployment operation. Credentials and complete
connection strings are not recorded in audit documents.

API Contract

No public API schema change. Internally, concurrent workers now receive
distinct claimable jobs instead of being able to claim the same pending row.

Database Migration

No schema change was required for concurrency-safe claiming.

During isolated test-database reconstruction, downgrading the graph-job
migration left the PostgreSQL `job_status` enum behind, causing the next
upgrade to fail until the orphaned type was removed. This migration downgrade
hygiene issue is not part of the MG-AUD-060 concurrency defect and remains an
explicit follow-up.

Scientific Impact

No scientific score, ranking, graph, pathway, or evidence semantic changed.
The remediation prevents duplicate execution of the same queued graph job
under concurrent workers.

Scope Boundary

MG-AUD-060 closes atomic pending-job claiming only. `complete_job()` and
`fail_job()` still permit contradictory lifecycle transitions and remain
tracked under MG-AUD-061.

Lessons Learned

Queue correctness must be verified on the production database dialect with
independent concurrent transactions. A passing single-session state-transition
test does not establish atomic multi-worker claiming.
